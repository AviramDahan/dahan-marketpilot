# Phase 16.2: End-to-End UAT & Operational Burn-in - Context

**Gathered:** 2026-06-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 16.2 proves the deployed Render + QuantConnect + Telegram Paper Trading product operates continuously under real market conditions. It does not add new strategies, real-money support, dashboard mutations, or v1.2 scope. It converts the already deployed product from "go-live verified" to "operationally proven" through multi-session evidence, failure handling, restart/redeploy recovery, and a final operational-readiness report.

</domain>

<decisions>
## Implementation Decisions

### Burn-In Window And Completion Gate

- **D-01:** Phase 16.2 is the final v1.1 production-readiness gate. v1.1 remains open until this phase produces external evidence for UAT-01 through UAT-09 and OPS-01.
- **D-02:** Burn-in should cover multiple consecutive real US market sessions. The recommended minimum is 2 consecutive valid US market sessions, with the planner allowed to extend to 3 if evidence is sparse or a market holiday/early close reduces signal quality.
- **D-03:** A session can count toward burn-in only if Render worker, Render dashboard, QuantConnect Paper deployment, shared state, and Telegram runtime path are all observable during that session.
- **D-04:** Do not fake signals, fills, orders, restart evidence, stale-data evidence, or failure evidence. Synthetic/offline tests may support local confidence, but external UAT rows must remain pending unless actually observed.
- **D-05:** The final output must be an operational-readiness report that distinguishes passed, failed, blocked, skipped, and not-run evidence. It must not claim profitability, expected returns, or real-money readiness.

### End-To-End Evidence Chain

- **D-06:** UAT-01 requires one traceable deployed flow: signal or explicit no-trade decision -> scoring/ranking -> risk decision -> Paper order path when eligible -> authoritative order result/fill/rejection -> sync -> shared state -> dashboard -> Telegram.
- **D-07:** If no real strategy signal appears naturally during the burn-in window, the phase may use the existing safe Object Store Paper smoke path only as an explicit operator-gated Paper-only probe. It must be labeled as a probe, not a strategy-generated production signal.
- **D-08:** QuantConnect remains the only authority for Paper orders, fills, rejections, cash, holdings, deployment status, and algorithm status. Dashboard and Render shared state are mirrors only.
- **D-09:** Order/fill/rejection evidence must use `/live/orders/read` or another already implemented authoritative QuantConnect wrapper. Live logs can support the narrative but cannot replace order authority.
- **D-10:** Dashboard proof must come from the deployed password-protected Render URL after login and must show source/freshness metadata, paper-only warning, and relevant portfolio/order/activity/system-health values.
- **D-11:** Telegram proof must use the production runtime notification dependency path. Telegram delivery remains observational and must not control safety, order, or recovery logic.

### Scheduler, Heartbeat, And Missed-Run Monitoring

- **D-12:** Scheduler heartbeat is a first-class burn-in artifact. Evidence must show fresh successful or attempted worker runs during valid market windows.
- **D-13:** GitHub Actions missed-run monitoring remains monitor-only. It may read heartbeat/dashboard health and report staleness, but it must never run scans, strategy evaluation, QuantConnect commands, or order code.
- **D-14:** Missed-run behavior should be proven through safe observation or controlled stale-heartbeat input. If inducing an actual missed production run would risk product operation, use a documented monitor-only simulation and keep external production missed-run evidence separate.
- **D-15:** Duplicate-run prevention must be verified through the durable shared lock/run-id path. The preferred proof is a safe controlled duplicate invocation or test harness that uses the same Render Key Value lock contract without creating duplicate Paper orders.

### Failure Handling And Recovery

- **D-16:** Restart/redeploy recovery should be proven by a controlled Render worker restart/redeploy and subsequent observation that scheduler heartbeat, shared state, dashboard freshness, and Telegram path recover without manual local machine participation.
- **D-17:** Temporary QuantConnect failure handling must be proven without damaging the active Paper deployment. Prefer a safe injected/fake client test plus, if possible, a read-only external outage/error observation. Real external failure evidence must never be fabricated.
- **D-18:** Telegram failure handling must be proven with a controlled bad-token/bad-chat or fake transport path that demonstrates delivery failure is reported while safety decisions and Paper Trading operation remain unaffected. Do not leave bad Telegram secrets deployed after the test.
- **D-19:** Stale-data handling must be proven on the deployed dashboard and/or verification script by observing or safely creating stale shared-state timestamps that render stale/error states without fabricating fresh data.
- **D-20:** Restart, failure, duplicate, stale, and missed-run evidence should each have a clear cleanup step and a "system restored" observation.

### Product Readiness Rules

- **D-21:** Phase 16.2 closes v1.1 only if the deployed product works while the local computer is not part of the runtime path. Evidence may include Render service pages, Render deploy logs, dashboard data, and worker heartbeat timestamps generated from Render.
- **D-22:** Production secrets remain in Render, QuantConnect, Telegram, GitHub, or local ignored operator env only. No raw token, password, account credential, chat ID, or deploy hook value may be committed or logged.
- **D-23:** Render dashboard remains read-only. The burn-in report may include screenshots/text observations, but no dashboard order controls, recovery buttons, export mutations, or Telegram-send controls may be added.
- **D-24:** Any unresolved external blocker must be reported as blocked/not-run with exact next action, not papered over. "Working product" is the definition of done, not completed code or planning.
- **D-25:** No future milestone, v1.2 creation, new strategies, broker integration, options/futures/crypto/Forex, or real-money functionality starts from this phase without explicit user approval.

### The Agent's Discretion

- Choose the exact evidence file names and report structure during planning, as long as they are committed under `.planning/phases/16.2-end-to-end-uat-operational-burn-in/` and do not contain secrets.
- Prefer scripts that output sanitized JSON status objects with `passed`, `failed`, `blocked_external_not_verified`, `skipped`, and `not_run` states.
- Prefer narrow, reversible external probes over broad manual tests.
- Prefer extending existing scripts (`verify_render_golive.py`, `telegram_runtime_smoke.py`, QuantConnect smoke helpers, heartbeat monitor) rather than inventing new operational paths.
- Choose whether evidence is gathered in one plan or split across waves, but external checks that need market sessions should be isolated so work can continue when markets are closed.

</decisions>

## Existing Code Insights

### Reusable Assets

- `ProductionRuntimeResult` and scheduler job result records already provide JSON-compatible run evidence for burn-in reports.
- `SchedulerHeartbeatRecord` and `evaluate_scheduler_heartbeat()` already model heartbeat/missed-run monitoring.
- `RenderKeyValueStore` already provides shared dashboard payload, activity records, and durable lock semantics across Render services.
- `verify_render_golive.py` and `telegram_runtime_smoke.py` already demonstrate the desired external-check pattern: explicit opt-in, sanitized JSON output, no mutation unless intentionally scoped.
- `qc_object_store_signal_smoke.py` already provides an operator-gated Paper-only probe for current-tag order/fill/rejection evidence.

### Established Patterns

- External evidence must be explicit and must preserve `not_run` / `blocked_external_not_verified` rather than pretending success.
- Render dashboard is read-only; QuantConnect is authoritative; Telegram is observational.
- Tests use deterministic fakes for local confidence and separate external scripts for real provider evidence.
- Secret values are redacted and must never be written to docs, logs, commits, or planning artifacts.

### Integration Points

- Phase 16.2 planning should wire verification around the deployed Render worker/dashboard rather than adding new runtime paths.
- Burn-in evidence should update Phase 16.2 UAT/Verification and likely a final operational-readiness report.
- GitHub Actions missed-run monitoring should remain monitor-only and should not become an execution scheduler.
- Any controlled failure injection should be reversible and should restore Render/Telegram/QuantConnect state before marking the wave complete.

</code_context>
