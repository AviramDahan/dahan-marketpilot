# Phase 16.1 Context: Production Integration & Dashboard Go-Live

## Phase

- Phase: 16.1 - Production Integration & Dashboard Go-Live
- Goal: Deploy Dahan MarketPilot as a fully operational personal autonomous Paper Trading product.
- Depends on: Phase 16 scheduler runtime exists. Phase 15 authoritative `/live/orders/read` order/fill/rejection gate remains open until a valid US market-hours or next-open observation window.
- Requirements: PROD-01, PROD-02, PROD-03, PROD-04, PROD-05, PROD-06, PROD-07, PROD-08, PROD-09, PROD-10, SAFE-06, SAFE-07.
- Mode: Discussion/context capture only. Do not start implementation until `/gsd-plan-phase 16.1` and `/gsd-execute-phase 16.1` are explicitly requested.

## Locked Decisions

- D-01: Phase 16.1 is the first production go-live phase. It must produce a working deployed personal Paper Trading product, not only local code, tests, or documentation.
- D-02: Phase 15 `/live/orders/read` order/fill/rejection authority remains pending and must not be closed, bypassed, faked, or marked complete by Phase 16.1.
- D-03: `PAPER_TRADING_ONLY`, read-only dashboard behavior, no real-money brokerage paths, no dashboard order entry, no hidden live-trading switch, and no secret leakage remain mandatory.
- D-04: Deploy the Streamlit dashboard as a Render Web Service and expose a working password-protected dashboard URL.
- D-05: Deploy the autonomous scheduler as the existing Render Background Worker (`dahan-marketpilot-scheduler`) so operation does not depend on the local computer.
- D-06: The production runtime runner from Phase 16 is the orchestration boundary. Phase 16.1 wires production dependencies into it; it must not duplicate strategy, scoring, risk, paper-order, or scheduler logic.
- D-07: Use Render Key Value / Valkey as the preferred shared durable production transport between worker and dashboard. It is accessible to multiple Render services and paid instances provide disk-backed persistence by default.
- D-08: Do not use Render Persistent Disk as the worker-dashboard shared transport. Render disks preserve files for one service only; a disk attached to one service cannot be accessed by another service.
- D-09: Keep QuantConnect as authoritative for portfolio, orders, fills, deployment state, and algorithm state. Shared storage is a dashboard/system-health mirror, not an authority source.
- D-10: Persist production dashboard exports as JSON-compatible records keyed by stable section names: portfolio, positions, trades/orders, fills, signals, activity, notifications, scheduler heartbeat, run ledger, and system health.
- D-11: The dashboard production mode must not use `data_source_kind=none`. It should read the shared production source and fail visibly with missing/stale/error states when data is unavailable.
- D-12: Dashboard auto-refresh should be controlled and conservative: enabled for operational viewing, configurable by env/config, and preserving existing stale/error states rather than hiding them.
- D-13: Telegram delivery must be connected to runtime notification events through the existing transport-neutral notification-event boundary. Telegram failure must not affect safety decisions or order logic.
- D-14: Secrets are configured only in Render environment variables, Render secret files, environment groups, QuantConnect, Telegram, or local operator env vars. No raw secret values may be committed, logged, summarized, or placed in docs.
- D-15: `render.yaml` should remain the infrastructure-as-code source for web service, background worker, and shared storage wiring where Render Blueprint support is appropriate. Secrets stay as `sync: false` placeholders or dashboard-managed values.
- D-16: Deployment verification must prove the local computer is off/not participating: the Render worker continues to produce heartbeat/data, and the Render dashboard reads it remotely.
- D-17: Phase 16.1 should include operator-facing runbook updates: dashboard URL, worker status, logs, restarts, secret setup, shared storage verification, rollback, and what remains blocked by market-hours gates.
- D-18: External verification is required for Phase 16.1 completion: Render services deployed, dashboard URL accessible with password, worker heartbeat observed, production data source configured, Telegram smoke delivered from runtime path, and local computer independence verified.
- D-19: Phase 16.2 remains responsible for multi-session burn-in, restart/redeploy recovery proof, temporary QuantConnect failure proof, Telegram failure proof, and final operational-readiness report.
- D-20: Do not create v1.2, add new strategies, add real-money support, add dashboard mutation controls, or expand into unrelated features.

## All Gray Areas Resolved

`/gsd-discuss-phase 16.1 --all` selected every gray area. The agent used the user's standing approval to choose recommended answers where interactive choices would otherwise be required.

| Gray area | Recommended decision |
|-----------|----------------------|
| Shared durable storage | Render Key Value / Valkey, not persistent disk, because disk is single-service scoped. |
| Dashboard data source | Real production shared store with typed degraded states; never `none` in production. |
| Worker-dashboard contract | JSON-compatible section records and heartbeat/system-health records keyed by stable names. |
| Telegram go-live | Wire real Telegram delivery through existing notification events; failures isolated from safety. |
| Render deployment | Use Blueprint/service config for dashboard web service, scheduler worker, and shared storage references. |
| Secrets | Render env vars/secret files/env groups only; no repository values; `sync: false` placeholders for per-service secrets. |
| Verification | External deployed checks are mandatory; local tests alone cannot complete 16.1. |
| Phase 15 dependency | Keep Phase 15 order-authority gate open and visible. |

## The Agent's Discretion

- Choose the exact Python adapter/module names for the shared storage layer during planning.
- Prefer a narrow adapter interface over spreading Redis/Valkey client calls through dashboard and runner code.
- Prefer stable JSON payloads compatible with existing `DashboardExportPayload`, `SchedulerHeartbeatRecord`, and scheduler ledger records.
- Prefer deterministic offline tests with fake shared storage and fake Telegram transport, plus explicit external verification scripts for Render.
- Choose whether to use Render Key Value via Blueprint references or manual Render Dashboard setup, but the runbook must clearly document any manual steps.
