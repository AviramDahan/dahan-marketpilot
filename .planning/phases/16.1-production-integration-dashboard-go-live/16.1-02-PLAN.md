# Phase 16.1 Plan 02: Production Runner Wiring

## Objective

Wire the existing Phase 16 production runner to real production adapters for shared state, durable lock, dashboard export, and Telegram delivery.

## Tasks

### Task 1: Persist runner outputs to shared state

Planned files: `marketpilot/production_runner.py`, `tests/test_production_runner.py`

- Add production sink wiring for dashboard section records, activity, run status, and heartbeat.
- Keep JSONL local files for local/offline tests, but allow production mode to use shared state.
- Ensure every shared record has run id, correlation id, timestamp, source authority, and paper-only metadata.
- Do not alter strategy, risk, or order-intent logic.

### Task 2: Add production Telegram notification sink

Planned files: `marketpilot/production_runner.py`, `marketpilot/telegram.py`, `tests/test_runtime_notification_emission.py`

- Create a production notification sink around `TelegramDeliveryService`.
- Persist safe Telegram delivery results to shared state/system health.
- Preserve dedup/rate-limit behavior where available.
- Prove Telegram failure does not change job safety status or order behavior.

### Task 3: Prepare durable lock path for Render Key Value

Planned files: `marketpilot/scheduler_lock.py`, `marketpilot/shared_state.py`, `tests/test_shared_state.py`, `tests/test_production_runner.py`

- Add lock operations through the shared store for Render deployment.
- Keep the existing file lock available for local deterministic operation.
- Prove overlap prevention works through the shared-store adapter.

## Verification

- `python -m pytest tests/test_scheduler_lock.py tests/test_scheduler_jobs.py -q`

## Success Criteria

- One deployed worker can run the full production pipeline through the Phase 16 runner.
- Dashboard export, heartbeat, activity, and Telegram results are persisted to the shared store.
- Notification delivery remains non-authoritative and safety-isolated.
