# Phase 16.1 Research: Production Integration & Dashboard Go-Live

## Scope

Phase 16.1 deploys the personal autonomous Paper Trading product. It wires the Phase 16 runner, dashboard, shared storage, Telegram, and Render services into a working production deployment.

It does not close the Phase 15 `/live/orders/read` order/fill/rejection authority gate. It does not start Phase 16.2 burn-in. It does not add strategies, real-money support, or dashboard mutation controls.

## Official Reference Findings

### Render Key Value / Valkey

- Render Key Value provides Redis-compatible shared storage that Render services can access through an internal URL.
- Newly created Key Value instances run Valkey 8.
- Paid Key Value instances support disk-backed persistence and enable it by default.
- Render recommends choosing the same region as connecting services to minimize latency and enable private-network communication.
- Render services connect via `REDIS_URL`; Python examples use `redis.from_url(os.environ["REDIS_URL"])`.
- For non-caching durable use cases, Render recommends Journal + Snapshot persistence.

Source: https://render.com/docs/key-value

### Render Persistent Disks

- Render service filesystems are ephemeral by default.
- Persistent disks preserve filesystem changes only for the service they are attached to.
- A persistent disk is accessible by only one service instance and cannot be accessed from another service.
- Therefore, persistent disks are not an appropriate shared transport between the dashboard web service and scheduler worker.

Source: https://render.com/docs/disks

### Render Blueprints And Secrets

- Render Blueprints can represent services and environment variables in `render.yaml`.
- Secret values must not be hardcoded; `sync: false` prompts for secret values in the dashboard.
- Render prompts for `sync: false` values during initial Blueprint creation; for existing services, new secret values may need to be added manually.
- Render environment variables and secret files are intended to keep credentials out of source code.

Sources:

- https://render.com/docs/blueprint-spec
- https://render.com/docs/configure-environment-variables

### Render Private Services / Background Workers

- Background workers are not reachable over the public internet or private network; they can initiate network requests but cannot receive incoming traffic.
- Render notes background workers often fetch work from a job queue backed by Key Value.
- This supports the Phase 16/16.1 boundary: the scheduler is a worker, and shared state must be in an external service such as Key Value rather than an inbound worker API.

Source: https://render.com/docs/private-services

## Existing Codebase Findings

- `marketpilot.production_runner.run_production_cycle()` already composes market guard, sync, runtime evaluation, paper delivery, order polling, dashboard export, notification, and heartbeat jobs.
- `marketpilot.scheduler_storage.JsonlSchedulerStorage` and `marketpilot.scheduler_lock.FileLockStore` define the local test/storage shape but are not shared between Render services.
- `marketpilot.scheduler_health.SchedulerHeartbeatRecord` and `evaluate_scheduler_heartbeat()` define the heartbeat contract Phase 16.1 should persist into the shared store.
- `dashboard.config.DashboardConfig` currently permits `none`, `local_json`, `object_store`, and `sync_jsonl`; Phase 16.1 needs a production source kind for Render Key Value and a guard that production cannot run with `none`.
- `dashboard.data.load_dashboard_snapshot()` already centralizes dashboard data loading; add the shared-source adapter there rather than spreading storage calls through Streamlit pages.
- `marketpilot.dashboard_export.DashboardExportPayload` provides JSON-compatible export records.
- `marketpilot.telegram.TelegramDeliveryService` already isolates delivery failures and redacts token/chat ids.
- `render.yaml` already defines the dashboard web service and scheduler worker; Phase 16.1 should add Key Value and env wiring.

## Planning Risks

- Shared storage durability must be explicit. Free Key Value instances are not suitable for production readiness if persistence is unavailable.
- The dashboard must not silently show fixtures, stale local files, or `data_source_kind=none` as production data.
- Render Blueprint `sync: false` values may need manual service configuration after existing service updates.
- Telegram delivery must be real for Phase 16.1, but failure cannot alter safety logic.
- External verification may require operator action in Render and cannot be faked by offline tests.
- Phase 15 market-hours authority remains a separate gate.

## Planning Conclusion

Plan Phase 16.1 as six plans across four execution waves:

1. Shared Render Key Value storage contracts and adapters.
2. Production runner wiring for shared storage, durable lock, dashboard export, Telegram sink, and config.
3. Dashboard production data source, auto-refresh, and read-only/stale handling.
4. Render Blueprint/secrets/runbook updates for dashboard, worker, and Key Value.
5. External verification scripts for Render URL, worker heartbeat, shared data, Telegram, and local-computer independence.
6. Go-live evidence, UAT docs, and Phase 16.1 closeout rules that keep Phase 15 and Phase 16.2 gates visible.
