# Phase 16.1 Patterns: Production Go-Live

## Reuse These Patterns

- Adapter boundary first: add a small shared-storage interface and one Render Key Value implementation instead of using Redis calls directly in runner/dashboard code.
- JSON-compatible records: preserve the current dashboard export, scheduler heartbeat, run ledger, and notification event shapes.
- Read-only dashboard: data loading belongs in `dashboard.data`; Streamlit pages stay display-only.
- Fail-visible production data: missing/stale/error states are displayed honestly; no fixture or `none` source may masquerade as production.
- Existing notification boundary: use `NotificationDomainEvent` and `TelegramDeliveryService`; do not add ad hoc Telegram calls in runner jobs.
- Render secrets by name only: docs and config list env var names, never values.
- External checks are evidence, not assumptions: Phase 16.1 cannot be complete until deployed checks produce sanitized evidence.

## Interfaces To Plan

- `SharedStateStore`: set/get JSON records, append recent activity, acquire/renew/release lock, read heartbeat.
- `RenderKeyValueStore`: Redis/Valkey-backed implementation using `REDIS_URL`.
- `DashboardSharedStoreLoader`: loads portfolio, signals, orders/fills, activity, notifications, and system health from shared records into `DashboardSnapshot`.
- `ProductionNotificationSink`: delivers runtime events through `TelegramDeliveryService`.
- `ProductionGoLiveVerifier`: scripts/checks for dashboard URL, auth, worker heartbeat, shared data, Telegram smoke, and no-local-computer operation.

## Test Strategy

- Offline tests use fake shared storage and fake Telegram transport.
- Render/Telegram/QuantConnect checks must be opt-in, credentialed, and produce sanitized output.
- Static tests reject dashboard mutation controls and secret-like committed values.
- Render blueprint tests validate service and Key Value wiring without deploying.
